# 0013. 结构化审查由 `github_pr_review` 工具编排证据，判断仍归模型

- 状态：Accepted
- 日期：2026-08-17

## 上下文

ADR-0012 决定把"一句 prompt 的 AI 审查"升级为结构化审查。参照物 `pr-review-toolkit` 的做法是六个专家 subagent（注释 / 测试 / 静默失败 / 类型设计 / 通用规范 / 简化）并行跑，各自带评分口径，最后聚合成 Critical / Important / Suggestion 行动计划。

dsh 侧要复刻这个效果，有三条路可走，差别在于"谁来保证审查覆盖了该覆盖的维度"：

- 靠 prompt 文本约束模型自己记住；
- 靠宿主编排，把维度拆解成可枚举的输入交给模型；
- 靠宿主自己调模型，工具直接返回结论。

第三条在本项目里不成立：seam 层没有模型访问通道，且 ADR-0002 已经确立过本项目的基本分工 —— 确定性信号（git 状态、文件分类）由宿主算，价值判断由模型做。

同时注意到一个事实：审查里真正确定性的部分不小。"这个 PR 改没改测试文件""改没改类型声明""哪些 hunk 落在 catch 块附近"都是可以由文件路径与 diff 文本确定性得出的，不需要模型猜；而"这个测试够不够""这个 catch 该不该吞"必须模型判断。

## 决策

新增 `github_pr_review` 工具，定位是**证据编排器，不是判断器**。一次调用返回三部分：

1. **维度路由**：按确定性规则（改动文件的路径与类型、diff 内容特征）判定本 PR 适用哪些维度，不适用的不下发 —— 没改测试就不发 `tests` 维度的空壳任务。
2. **分维度证据包**：每个维度只带该维度需要的 diff 切片与上下文，而非把全量 diff 重复六遍。diff 预算沿用 ADR-0005 的机制（consumer 持有数值、seam 执行截断、`truncated` 诚实）。
3. **审查契约**：每个维度的 checklist 与严重度口径（`blocker` / `major` / `minor` / `nit`），以及输出格式要求（每条 finding 必须带 `path:line`、问题陈述、依据、建议）。

模型据此产出 findings；工具不解析、不评分、不裁决。审查结论要回到 PR 时，由模型另行调用 review 提交工具（ADR-0014）。

`dsh-ui-github` 状态条的 [AI 审查] 按钮继续走 `shell.prompt`（ADR-0011 已确立的通路），prompt 改为引导模型调用 `github_pr_review` —— 按钮不新增直连宿主的路径。

## 备选方案

- **仅升级 prompt 文本**：零新机制，但维度覆盖全靠模型记性，长 prompt 在长 diff 面前会被稀释；且无法做维度路由，短 PR 也要背全套六维度清单。
- **宿主内部跑多轮模型（仿 subagent 并行）**：最贴近参照物，但 seam 无模型访问，要么让连接器直接持有 API key（与凭据边界冲突），要么反向依赖 agent 层（破坏 host/preset 分层）。dsh 是否提供可复用的 subagent 机制未经核实，不作为设计前提。
- **六个独立工具（`github_pr_review_tests` 等）**：工具目录膨胀六倍，且模型需要自己判断该调哪几个 —— 维度路由这件确定性的事又被推回给模型。
- **工具返回结论（宿主打分）**：确定性规则打不出"这个测试够不够"，只会产出机械的伪评分。

## 后果

- 审查质量的上限仍取决于模型，工具保证的是**覆盖面与输出形状可复现**，不保证结论正确 —— 这是有意的定位，文档与 README 的 `## Model Experience` 章节需如实描述，避免读者误以为工具本身在审查。
- 一次 `github_pr_review` 的返回体积明显大于 `github_pr_read`，预算参数需要独立的默认值（不复用 `github_pr_read` 的 `maxFiles: 50` / `maxPatchChars: 60000`），具体数值在执行计划 M9 定。
- 维度路由是确定性代码，可完整单测（给定文件清单 → 期望维度集合），这是把它放在宿主的直接收益。
- 维度集合是闭合联合，消费端 `switch + assertNever`；新增维度是一次 seam 变更，不能由配置注入任意字符串。
